# RFC 051: Flatpak distribution, and what a sandbox changes

**Status:** **Accepted by the project owner, 2026-10-22** (*"Accepted."*).
**No implementing task has been written**, and none should be yet — §5 sequences
this after the AUR channel serves a real package. Acceptance of the RFC is not
authorization of work, per the project's standing rule.
**Raised by:** the owner, 2026-10-21 — *"I got interested in publishment on
FlatPak via GitHub. It will bring the product to a broader range of Linux
users."*
**Relates to:** [RFC 030](../done/030-distribution-and-version-contracts.md),
[RFC 032](../done/032-ffmpeg-absence-contract.md),
[RFC 041](../done/041-application-data-locations.md),
[RFC 042](./042-windows-store-distribution.md)

## Summary

Flathub is how most Linux desktop users install software, so the reach argument
is right. **arama turns out to be unusually close to sandbox-ready** — three of
the things that most often block a Flatpak are already correct in our code, by
accident rather than design, and two more were produced in the last fortnight
for other reasons.

What is left is **three decisions**, not a procedure. This RFC states them. It
does not propose a timeline; §5 argues it should follow the AUR channel actually
going live.

## 1. What already works, verified rather than assumed

| Concern | Finding | Checked |
|---|---|---|
| Folder selection | `rfd` 0.17's default features are `xdg-portal` + `wayland`, and its backend talks to `org.freedesktop.portal.Desktop` directly | `rfd-0.17.2/src/backend/xdg_desktop_portal/portal/` |
| Data locations | `ProjectDirs::from("", "", "arama")` resolves through `XDG_DATA_HOME`, which Flatpak redirects to `~/.var/app/<id>/data` | `env/src/dir.rs:47` |
| ffmpeg | Discovery scans `PATH`; a bundled ffmpeg at `/app/bin` is on the sandbox `PATH`, so `FfmpegLocationPreference::Auto` finds it | `env/src/config/settings/ffmpeg_location.rs`, sidecar discovery |
| Runtime libraries | All twelve `dlopen`'d sonames (dbus, EGL, vulkan, wayland, X11, xcb, Xcursor, Xi, xkbcommon…) are in `org.freedesktop.Platform` | T054's derived list, re-confirmed in T060 |
| Screenshots | Eight at 1560×1020, EN + JA | T057 |
| Icon | 32/48/64/128/256 plus a 300×300 source | T056 |
| Privacy text | Required because the app requests network | `PRIVACY.md` |

**Portal-based folder selection is the important one.** It means arama can ask
for a directory through the portal rather than holding `--filesystem=home`, which
is both the better design and the thing Flathub reviewers look for.

**The ffmpeg concern dissolves, and RFC 032 is untouched.** Bundling ffmpeg in
the Flatpak is the *packager* including it, exactly as a distro package does —
arama still never downloads or installs it on the user's behalf, which is what
RFC 032 actually forbids. No code change.

## 2. The three decisions

### 2.1 The offline build, and its per-release cost

Flathub builds are network-isolated. Every one of **705 crate dependencies**
must be declared as a source, generated by `flatpak-cargo-generator.py` into a
large JSON manifest that is **regenerated for every release**. `aws-lc-sys` and
`candle` additionally need `cmake`, `nasm` and `perl` present in the SDK.

**This is the real engineering cost and it recurs.** The owner excluded CI
automation for AUR; Flathub adds a third channel with a per-release mechanical
step that is unpleasant to do by hand and easy to do stale.

**The decision:** accept a recurring manual step, or revisit the
CI-automation exclusion for packaging generally. Deferring it means the first
stale release is how we find out.

### 2.2 `root_dir_path` persistence — convenience, not correctness

> **Corrected 2026-10-24. The original version of this section was wrong**, and
> the owner accepted this RFC partly on the strength of it. It claimed arama
> would "display a library root it remembers and silently be unable to read it",
> indistinguishable from an empty directory, and that this already happened on
> every platform with an unmounted share or a removed drive.
>
> **arama already detects this and says so.** The claim was asserted from
> `settings.rs:42` without reading the startup path. Verified since:

`env/src/config/settings.rs:42` persists `root_dir_path: String` and reopens it
on launch — and `startup_dir_node` (`app/src/core.rs:462`) checks it before
anything else. Both failure modes are already handled and surfaced:

| Case | `Path::is_dir()` | What the user gets |
|---|---|---|
| Missing, unmounted share, removed drive | `false` | `startup.root_dir_unavailable` — *"Startup folder unavailable / The saved folder cannot be opened. Choose another folder to start indexing"*, with the path |
| Present but unreadable (permission denied) | `true`, `read_dir` fails | `startup.root_scan_warning`, via `swdir::WalkError::Io` which documents covering *"read_dir failing outright (e.g. permission denied, not found)"*, with the path |

Both keys exist in **both** locales, both are pushed as startup toasts through
`push_startup_notices` (`core.rs:242`), and `dir_node: None` stops indexing from
starting on a bad root. Verified empirically: a missing directory gives
`is_dir() == false`; a `chmod 000` directory gives `is_dir() == true` with
`read_dir` failing — so the two notices cover the two cases between them.

**So the honest-failure requirement is already met, on every platform, today.**
There is no defect here and no cross-platform work to schedule.

**What remains is Flatpak-only and is convenience, not correctness.** A
portal-granted path may not be re-openable after a restart, so a sandboxed arama
would show the "Startup folder unavailable" notice and ask the user to pick the
folder again — correct behaviour, and irritating every launch.

**Options, for the Flatpak work only:**

- **(a) Use the portal's persistent permissions**, so the grant survives a
  restart and the notice does not fire. The right answer; the most work.
- **(b) Accept re-picking.** Honest, already implemented, mildly annoying.
- **(c) `--filesystem=home`.** Removes the sandbox's point; Flathub review
  discourages it and it contradicts §1's portal finding. Rejected.

**Recommendation: (a), scoped inside the Flatpak work.** Nothing here is
liftable into a separate cross-platform task, which is what the corrected
version of this section changes.

### 2.3 Network permission for the model download

The Flatpak needs `--share=network`, because the first run downloads two models
from `huggingface.co`. This is allowed and common, but it is declared in the
manifest and reviewers ask about it.

**We are well placed to answer:** `PRIVACY.md` already states exactly what the
connection is, what is not sent, and that analysis afterwards needs no network.
The AppStream metainfo should carry the same statement so it is visible before
install, not after.

**The decision is whether that is acceptable at all**, or whether Flatpak should
ship models in the image. Shipping them would add ~605 MB to the Flatpak, remove
the network permission, and conflict with
[RFC 021](../done/021-clip-safetensors-source-strategy.md)'s sourcing strategy
and with [RFC 046](./046-audio-model-fidelity.md), which may change which model
is shipped at all. **Recommendation: download at runtime, as today.** Revisit
only if RFC 046 lands on a much smaller model.

## 3. What Flathub requires that we do not have

- **An AppStream metainfo file** — `io.github.nabbisen.arama.metainfo.xml`, with
  summary, description, launchable, developer, content rating, release history
  and screenshots. The screenshots and the description text exist; the file does
  not.
- **A desktop file and icons named for the app ID.** Ours are `arama.desktop`
  and `arama.png`; Flatpak wants `io.github.nabbisen.arama.*`. Mechanical, but
  it means a third naming scheme beside the AUR's and the Store's.
- **The app ID itself.** `io.github.nabbisen.arama` is available to a
  GitHub-hosted project **without owning a domain** — which matters, because a
  domain would mean registration details, and the owner has been explicit about
  not creating new exposure of that kind.

## 4. Non-goals

- **CUDA.** The Flatpak is CPU-only. The CUDA variant stays a GitHub asset; this
  is the same reasoning RFC 042 reached for the Store.
- **Replacing the GitHub release assets or the AUR packages.** A fourth channel,
  not a substitute.
- **Automating Flathub submission.** Out of scope here for the same reason AUR
  automation is — the owner excluded it; §2.1 is where that gets revisited if it
  is going to be.
- **Bundling the AI models.** §2.3.

## 5. Sequencing — why not now

**Both AUR packages are still placeholders at `0.0.0-1`.** Standing up a third
channel while the second has never served a real package would leave two
incomplete channels instead of one working one, and the AUR work is the shorter
path to the same goal — owner task 003 is written and waiting.

**Recommended order:** finish 0.43.0 (T061 is the only remaining item) → publish
the AUR packages for real → then this.

That order also de-risks §2.1: the AUR packages are the first test of whether a
manual per-release packaging step actually gets done, and the answer should
inform whether Flathub's heavier one is taken on by hand.

## 6. Acceptance

- A Flatpak builds offline from a generated cargo sources manifest, on
  Flathub's own infrastructure.
- The folder picker works through the portal, without `--filesystem=home`.
- A remembered root that is no longer accessible produces a distinct, stated
  condition — never an empty gallery (§2.2, and this holds on every platform).
- Video similarity works out of the box, with bundled ffmpeg found by `Auto`
  discovery and **no arama code change** to the sidecar.
- Models download on first run, with the network permission declared and
  explained in the metainfo.
- The metainfo validates and the listing shows the T057 screenshots.

## 7. Open questions

- **Does a Flatpak diverge from the documented ffmpeg contract in a way users
  should be told about?** On Flatpak video works immediately; everywhere else
  the user installs ffmpeg themselves. That is a better experience and an
  inconsistency at the same time. It is a documentation question, not a code
  one, but it should be answered deliberately rather than discovered.
- **Who owns the per-release update?** Flathub's external-data-checker can open
  the PR automatically for a GitHub-release-driven manifest; whether to use it
  is §2.1's decision in another form.
